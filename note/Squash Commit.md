### Squash Commit: 실무 적용 시나리오와 해결 방법

**1. 예시 상황 (문제 발생)**

개발자 A가 `feature/login` 브랜치를 생성하여 새로운 로그인 기능을 개발하고 있습니다. 작업 중 작업물을 잃어버리지 않기 위해 습관적으로 여러 번 커밋을 남겼습니다. 현재 브랜치에는 다음과 같은 4개의 커밋이 쌓여 있습니다.

- `commit 1`: feat: 로그인 화면 UI 마크업
    
- `commit 2`: fix: 로그인 버튼 텍스트 오타 수정
    
- `commit 3`: test: API 통신 테스트 진행 중...
    
- `commit 4`: feat: 로그인 API 연동 및 검증 완료
    

**2. 왜 Squash를 사용해야 하는가? (문제점)**

위 4개의 커밋을 그대로 공용 브랜치(`dev`나 `PRD`)에 병합하면, "오타 수정", "테스트 진행 중"과 같은 불필요한 중간 작업 내역(Working In Progress)이 모두 섞이게 됩니다. 이런 상태로 작업 내역이 누적되면 전체 커밋 히스토리가 지저분해져 시스템 흐름을 파악하기 힘들어집니다. 특히 여러 사람이 협업하는 환경에서는 이슈를 추적하거나 장애 발생 시 특정 버전을 롤백해야 할 때 큰 방해 요소가 됩니다.

**3. 해결 방법 (Squash 적용)**

Squash를 사용하면 이 4개의 자잘한 커밋을 하나의 의미 있는 커밋으로 정리할 수 있습니다. 즉, 자잘한 이력들을 숨기고 **"feat: 로그인 기능 최종 구현"** 이라는 1개의 깔끔한 이력으로 압축하는 것입니다.

**[해결 절차: 타 브랜치로 병합할 때 `merge --squash` 활용]**

가장 직관적으로 병합 기록을 깔끔하게 남기는 방법입니다.

Bash

```
# 1. 병합의 목적지인 dev 브랜치로 이동합니다.
git checkout dev

# 2. feature/login 브랜치의 4개 커밋 변경사항을 합쳐서, 커밋 직전인 '스테이징(add)' 상태로만 가져옵니다.
git merge --squash feature/login

# 3. 기존의 자잘한 메시지들을 무시하고, 새로운 단일 커밋 메시지로 최종 저장합니다.
git commit -m "feat: 로그인 기능 최종 구현"
```

이렇게 처리하면 기존의 지저분한 4개 커밋은 `feature/login` 브랜치에만 남아있게 되고, 공용 브랜치인 `dev`에는 방금 작성한 단 1개의 완성된 커밋만 깔끔하게 기록됩니다.

### 방법 1: 로컬에서 Squash 후 원격에 강제 푸시하기 (Interactive Rebase)

MR을 요청하기 전에 내 PC(로컬)에서 지저분한 커밋을 하나로 합친 뒤, 원격 `feature/test1` 브랜치에 덮어쓰는 방법입니다.

**1. 예시 상황 시나리오**

현재 로컬 `feature/test1` 브랜치에서 작업을 마쳤으며, 최근 3개의 커밋이 쌓여있습니다. 이미 원격(`origin/feature/test1`)에도 이 3개의 커밋이 푸시되어 있는 상태입니다.

- `commit 1`: feat: 로그인 로직 기초 작성
    
- `commit 2`: fix: 변수명 오타 수정
    
- `commit 3`: test: 로그인 성공 케이스 테스트 완료
    

**2. 해결 절차 (명령어 가이드)**

Bash

```
# 1. 최근 3개의 커밋 이력을 합치기 위해 텍스트 에디터를 엽니다.
git rebase -i HEAD~3
```

에디터가 열리면 아래와 같이 3줄의 커밋이 보입니다. 가장 오래된 커밋이 맨 위에 위치합니다.

Plaintext

```
pick 1a2b3c4 feat: 로그인 로직 기초 작성
pick 5d6e7f8 fix: 변수명 오타 수정
pick 9g0h1i2 test: 로그인 성공 케이스 테스트 완료
```

첫 번째 기준 커밋은 `pick`으로 그대로 두고, 합칠 나머지 커밋 앞의 `pick`을 `squash`(또는 `s`)로 변경한 후 저장(wq)합니다.

Plaintext

```
pick 1a2b3c4 feat: 로그인 로직 기초 작성
s 5d6e7f8 fix: 변수명 오타 수정
s 9g0h1i2 test: 로그인 성공 케이스 테스트 완료
```

이어서 커밋 메시지를 수정하는 새로운 에디터 창이 열립니다. 기존의 지저분한 3개의 메시지를 지우고, 하나의 깔끔한 메시지로 변경한 후 저장합니다.

Plaintext

```
feat: 로그인 기능 최종 구현 완료
```

Bash

```
# 2. 로컬에서 하나로 압축된 새로운 커밋을 원격 저장소에 반영합니다.
# 주의: 이미 원격에 올라가 있던 예전 3개의 커밋 히스토리를 
# 방금 만든 1개의 새 히스토리로 '덮어써야' 하므로 반드시 강제 푸시(-f)가 필요합니다.
git push origin feature/test1 -f
```

이제 GitLab에 들어가서 `feature/test1` 브랜치를 확인해 보시면, 기존 3개의 커밋이 사라지고 1개의 깔끔한 커밋으로 변경되어 있습니다. 이 상태로 `dev` 브랜치로 MR을 올리시면 됩니다.

### 방법 2: GitLab UI를 활용한 Squash Merge (권장 대안)

사실 최신 CI/CD 환경에서는 로컬에서 터미널 명령어로 복잡하게 이력을 조작하는 것보다, **GitLab 자체 기능**을 활용하는 것을 훨씬 더 권장합니다.

**1. 예시 상황 시나리오**

로컬에 "오타 수정", "WIP" 등 지저분한 커밋 10개가 있든 20개가 있든 신경 쓰지 않고, 그냥 그대로 원격 `feature/test1`에 모두 푸시(`git push`)해 버린 상태입니다.

**2. 해결 절차 (GitLab MR 설정)**

1. GitLab 웹에 접속하여 `feature/test1` -> `dev` 방향으로 **Merge Request를 생성**합니다.
    
2. MR 작성 화면 하단(또는 MR 승인 화면)을 보면 **Merge options**라는 항목이 있습니다.
    
3. **`Squash commits when merge request is accepted`** 체크박스에 체크합니다.
    
4. MR을 담당자가 승인(Merge)하는 순간, GitLab이 알아서 `feature/test1`에 있던 지저분한 커밋 10개를 1개의 커밋으로 깔끔하게 뭉친(Squash) 후 `dev` 브랜치에 병합합니다.
    

> **💡 관련 기술 트렌드 및 주의점**
> 
> - **트렌드:** 최근에는 개발자의 명령어 실수로 인한 형상 꼬임을 방지하기 위해, 명령어(방법 1) 대신 플랫폼에서 제공하는 기능(방법 2)을 사용하는 것이 실무 표준으로 자리 잡고 있습니다.
>     
> - **주의점:** 방법 1에서 사용하는 `push -f` (강제 푸시)는 오직 '나 혼자 작업하는 feature 브랜치'에서만 사용해야 합니다. 다른 사람과 함께 작업 중인 브랜치에서 강제 푸시를 하면 동료들의 로컬 소스코드가 엉키는 대참사가 발생합니다.
>     

설명해 드린 두 가지 방법 중, 터미널에서 직접 이력을 제어하는 **방법 1**과 GitLab UI를 통해 안전하게 처리하는 **방법 2** 중 현재 팀의 협업 컨벤션에 더 부합하는 방식은 어느 쪽입니까? (필요하시다면 `rebase -i` 시 열리는 Vim 에디터 조작법 등 세부적인 내용을 추가로 안내해 드리겠습니다.)
