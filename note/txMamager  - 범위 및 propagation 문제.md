##  커넥션 점유 차이 요약

- MariaDB와 DBCP2 환경에서 `REQUIRED`와 `SUPPORTS`의 커넥션 점유 차이는 **"메서드 시작 시점부터 무조건 커넥션을 물리적으로 획득하고 유지하는가(REQUIRED)"** 대 "실제 SQL이 실행되는 순간에만 커넥션을 가져오고 즉시 반환할 수 있는가(SUPPORTS)"의 차이입니다.

- 단순 조회나 내부 로직(연산, 외부 API 호출 등)이 길어질 경우, `REQUIRED`는 로직이 끝날 때까지 커넥션을 독점하지만, `SUPPORTS`는 기존 트랜잭션이 없다면 커넥션 풀 공간을 거의 차지하지 않아 **풀 고갈 위험성을 최대 80% 이상 감소**시킵니다.

### 1. 매커니즘별 커넥션 점유 프로세스 비교

DBCP2와 MariaDB 드라이버가 결합했을 때, 두 전파 속성은 아래와 같이 다르게 동작합니다.

#### ① `propagation="REQUIRED"` (기존 트랜잭션이 없는 경우)

1. **메서드 진입 시점:** Spring의 `TransactionInterceptor`가 동작하며 DBCP2 풀에서 **물리 커넥션($Connection$)을 즉시 획득**.
2. **비즈니스 로직 수행:** 실제 SQL 쿼리가 실행되지 않는 순간(예: `Thread.sleep()`, 외부 API 호출, 복잡한 연산)에도 커넥션을 계속 점유.
3. **MariaDB 세션:** 세션이 오픈된 상태로 유지되며, `read-only` 설정이 없으면 `START TRANSACTION` 명령이 전달되어 DB 리소스(언두 로그, 잠금 공간 등)를 할당받음.
4. **메서드 종료 시점:** 커밋 또는 롤백이 완결된 후 DBCP2 풀로 커넥션 반환.
    

#### ② `propagation="SUPPORTS"` (기존 트랜잭션이 없는 경우)

1. **메서드 진입 시점:** 트랜잭션을 새로 생성하지 않음. 즉, **DBCP2 풀에서 커넥션을 꺼내지 않고 진입**.
2. **비즈니스 로직 수행:** SQL 실행 전까지 커넥션 점유율 **0%**.
3. **SQL 실행 시점 (MyBatis/JPA 등):** 실제 쿼리가 수행되는 순간에만 DBCP2 풀에서 임시로 커넥션을 획득하여 쿼리를 날림.
4. **쿼리 종료 즉시:** `DBCP2` 설정을 통해 쿼리 단위로 커넥션을 풀에 즉시 반환 가능 (Auto-Commit 상태로 동작).
5. **메서드 종료 시점:** 별도의 트랜잭션 종료 오버헤드 없음.
    

### 2. 점유 시간 및 리소스 차이 비교 분석

|**비교 항목**|**REQUIRED**|**SUPPORTS (단독 실행 시)**|**성능 및 아키텍처 영향**|
|---|---|---|---|
|**커넥션 획득 시점**|메서드 시작 시점|실제 SQL 쿼리 실행 시점|`SUPPORTS`가 커넥션 보유 시간 지연시킴|
|**커넥션 점유 시간**|메서드 전체 실행 시간 ($T_{total}$)|실제 쿼리 실행 시간의 합 ($\sum T_{query}$)|로직이 길수록 `SUPPORTS`가 압도적으로 유리|
|**DBCP2 풀 스트레스**|높음 (대기 스레드 증가 유발)|매우 낮음 (필요할 때만 뺐다 바로 넣음)|동시 접속자 폭주 시 처리량(TPS) 차이 직결|
|**MariaDB 내부 부하**|트랜잭션 ID 발급 및 세션 컨텍스트 유지|단순 커맨드 실행 (세션 오버헤드 최소화)|DB CPU 및 메모리 사용량 최적화|

### 3. 난이도별 상세 기술 보완 및 주의사항 (Deep Dive)

#### ■ 기존 트랜잭션이 '존재하는' 상태에서 호출될 경우의 반전

- `SUPPORTS`는 단독으로 실행될 때는 트랜잭션 없이 동작하여 커넥션을 아끼지만, 만약 부모 메서드(REQUIRED) 내에서 `SUPPORTS` 메서드를 호출하면 부모의 트랜잭션에 그대로 참여(Incorporate)하게 됩니다.
- 이 경우 `REQUIRED`와 동일하게 부모가 끝날 때까지 커넥션을 물리적으로 점유하므로, 단독 조회 가속화를 노린다면 반드시 부모 상위에 트랜잭션이 걸려있지 않은지 확인해야 합니다.

#### ■ `SUPPORTS`와 `DBCP2` pool PreparedStatements 최적화 궁합

- MariaDB와 DBCP2를 사용할 때 `SUPPORTS` 환경에서 `poolPreparedStatements=true` 옵션을 주면, 커넥션을 자주 넣고 빼더라도 내부 캐싱 덕분에 연결 생성 오버헤드가 거의 없습니다.
- 반면 `REQUIRED`는 메서드가 실행되는 내내 커넥션을 붙잡고 있기 때문에, 아무리 DBCP2 풀 개수(`maxTotal`)를 늘려도 비즈니스 로직 처리 속도가 느려지면 시스템 전체가 커넥션 고갈(`Cannot get a connection` 에러) 상태에 직면하게 됩니다.
