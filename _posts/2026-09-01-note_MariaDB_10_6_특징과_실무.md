## 1. MariaDB 10.6 동시성 처리 제어와 Spring Framework 5.3 실무 적용 가이드
## 2. 먼저 결론
MariaDB 10.6에서 동시성 제어의 핵심은 **InnoDB + MVCC + Transaction Isolation + Row/Index Lock**입니다. InnoDB는 ACID 트랜잭션, 행 수준 잠금, MVCC 기반 읽기를 제공하며 OLTP에 적합합니다. 
커머스 시스템에서는 아래 순서로 접근하는 것이 좋습니다.

| 우선순위 | 방법                      | 권장 용도                    |
| ---: | ----------------------- | ------------------------ |
|    1 | 원자적 `UPDATE`            | 재고 차감, 카운터 증가/감소         |
|    2 | `UNIQUE` 제약조건           | 중복 주문/결제/요청 방지           |
|    3 | 낙관적 Lock(version)       | 상품/주문 상태 변경              |
|    4 | `SELECT ... FOR UPDATE` | 읽은 값을 기준으로 복합 판단이 필요한 경우 |
|    5 | `SKIP LOCKED`           | 다중 배치/Worker 작업 분배       |
|    6 | Isolation Level 조정      | Gap Lock 등 구조적인 경합 해결    |
|    7 | SERIALIZABLE            | 극히 제한적인 업무               |
- **가장 중요한 원칙은 Lock을 많이 거는 것이 아니라 Lock을 짧고 정확하게 거는 것입니다.**

## 3. MariaDB 동시성 제어 전체 구조
MariaDB 10.6 + InnoDB에서는 대략 다음 구조로 동시성을 처리합니다.
```text
Application Thread
        │
        ▼
Spring @Transactional
        │
        ▼
JDBC Connection
        │
        ▼
MariaDB Transaction
        │
        ├─ Isolation Level
        │    ├─ READ UNCOMMITTED
        │    ├─ READ COMMITTED
        │    ├─ REPEATABLE READ ← 기본값
        │    └─ SERIALIZABLE
        │
        ├─ MVCC
        │    └─ Consistent Read
        │
        └─ InnoDB Lock
             ├─ Record Lock
             ├─ Gap Lock
             ├─ Next-Key Lock
             ├─ Shared Lock
             └─ Exclusive Lock
```
MariaDB의 InnoDB 기본 Isolation Level은 `REPEATABLE READ`입니다. MariaDB 10.6에서는 확인 변수로 `tx_isolation`을 사용해야 합니다. `transaction_isolation`이라는 시스템 변수명은 MariaDB 11.1.1부터 도입됐습니다. 
```sql
SELECT @@GLOBAL.tx_isolation;
SELECT @@SESSION.tx_isolation;
```
일반적으로 결과는 다음과 같습니다.
```text
REPEATABLE-READ
```

## 4. MVCC가 무엇인가
MVCC는 **Multi Version Concurrency Control**입니다.
예를 들어 다음 데이터가 있다고 가정합니다.
```text
상품 A 재고 = 10
```
Transaction A:
```sql
BEGIN;
SELECT stock
FROM product_stock
WHERE product_id = 100;
-- 10
```
Transaction B:
```sql
BEGIN;
UPDATE product_stock
SET stock = 9
WHERE product_id = 100;
COMMIT;
```
Transaction A가 `REPEATABLE READ`라면 다시 조회해도 일반적인 Consistent Read에서는:
```sql
SELECT stock
FROM product_stock
WHERE product_id = 100;
```
첫 번째 `SELECT`가 만든 Snapshot을 기준으로 같은 트랜잭션 내에서는 계속 `10`을 볼 수 있습니다. 이것이 MVCC입니다. MariaDB의 `REPEATABLE READ`에서는 첫 consistent read에서 만든 snapshot을 후속 consistent read가 공유합니다. 
즉:
```text
MVCC ≠ Lock
```
입니다.
일반적인:
```sql
SELECT ...
```
는 Snapshot을 보는 **Consistent Read**입니다.
반면:
```sql
SELECT ...
FOR UPDATE
```
는 현재 레코드를 대상으로 하는 **Locking Read**입니다.
- 이 차이를 이해하지 못하면 실무에서 동시성 오류가 많이 발생합니다.

## 5. Isolation Level
### 5-1. 비교
|Isolation|Dirty Read|Non-repeatable Read|동일 트랜잭션 Snapshot|Lock 경합|실무 추천|
|---|---:|---:|---:|---:|---|
|READ UNCOMMITTED|가능|가능|약함|낮음|거의 사용하지 않음|
|READ COMMITTED|방지|가능|SELECT마다 신규 Snapshot|상대적으로 낮음|고동시성 OLTP 검토|
|REPEATABLE READ|방지|방지|트랜잭션 Snapshot|중간|MariaDB 기본값|
|SERIALIZABLE|방지|방지|강함|매우 높음|특수 업무만|
MariaDB InnoDB의 기본값은 `REPEATABLE READ`이며, `READ COMMITTED`는 매 consistent read마다 새로운 snapshot을 사용합니다. `SERIALIZABLE`은 autocommit이 꺼진 상태에서 일반 SELECT까지 `LOCK IN SHARE MODE`에 가까운 방식으로 처리하기 때문에 동시성이 크게 떨어질 수 있습니다. 
### 5-2. 커머스 시스템에서는?
- 기본적으로
```text
REPEATABLE READ
```
를 그대로 사용하는 것도 충분히 가능합니다.
다만 다음과 같은 문제가 지속적으로 발생한다면:
```text
Deadlock 증가
Lock Wait 증가
범위 UPDATE 경합
FOR UPDATE 범위 조회 경합
동시에 INSERT가 많은 테이블
```
`READ COMMITTED` 검토 가치가 있습니다.
하지만 **Deadlock이 발생한다고 바로 전체 DB를 READ COMMITTED로 변경하는 것은 권장하지 않습니다.**
우선 확인할 사항은:
```text
1. 잘못된 인덱스
2. 지나치게 넓은 UPDATE 범위
3. 긴 Transaction
4. 서로 다른 Lock 획득 순서
5. SELECT → Java 계산 → UPDATE 구조
6. Transaction 안에서 외부 API 호출
```

## 6. InnoDB Lock 종류
### 6-1. Record Lock
실제 행 자체라기보다 **Index Record에 Lock을 설정합니다.** InnoDB는 논리적인 테이블 행보다 Index Record 기반으로 Lock을 처리한다는 점이 매우 중요합니다. 
예:
```sql
UPDATE product
SET price = 10000
WHERE product_id = 100;
```
`product_id`가 PK라면:
```text
PRIMARY INDEX
product_id=100
```
에 Exclusive Record Lock이 걸립니다.
### 6-2. Shared Lock(S)
```sql
SELECT *
FROM product
WHERE product_id = 100
LOCK IN SHARE MODE;
```
다른 트랜잭션도 Shared Lock은 얻을 수 있지만 변경을 위한 Exclusive Lock과 충돌합니다. 
실무에서는 `FOR UPDATE`보다 사용 빈도가 낮습니다.
### 6-3. Exclusive Lock(X)
다음과 같은 작업에서 사용됩니다.
```sql
UPDATE
DELETE
SELECT ... FOR UPDATE
```
동일 Index Record에 대한 다른 X Lock 획득을 막습니다. 일반 Snapshot SELECT는 MVCC로 이전 버전을 읽을 수 있으므로 반드시 대기한다는 의미는 아닙니다. 
### 6-4. Gap Lock
가장 주의해야 합니다.
데이터:
```text
10
20
30
```
조건:
```sql
SELECT *
FROM product
WHERE id BETWEEN 10 AND 30
FOR UPDATE;
```
`REPEATABLE READ`에서는 단순히:
```text
10
20
30
```
만 Lock하는 것이 아니라 인덱스 구간의 Gap도 Lock 대상이 될 수 있습니다.
```text
10 ---- 20 ---- 30
   GAP     GAP
```
따라서 다른 트랜잭션의:
```sql
INSERT id = 15;
```
같은 INSERT가 대기할 수 있습니다. Gap Lock은 phantom을 방지하기 위한 InnoDB의 중요한 메커니즘이며, `READ COMMITTED`에서는 대부분의 일반 검색 Gap Lock이 제거되는 방향으로 동작합니다. 
### 6-5. Next-Key Lock
```text
Record Lock + Gap Lock
```
입니다.
```text
Gap        Record
--------- [20]
      Next-Key Lock
```
범위 조건:
```sql
WHERE price >= 10000
WHERE created_at BETWEEN ...
WHERE status = 'READY'
```
- 등에서 특히 중요합니다.

## 7. 인덱스가 동시성 성능을 결정한다
이 부분이 매우 중요합니다.
다음 SQL:
```sql
UPDATE orders
SET status = 'DONE'
WHERE order_no = '202609010001';
```
### 7-1. order_no에 인덱스가 존재
```text
INDEX 검색
→ 필요한 Record만 접근
→ Lock 범위 작음
```
### 7-2. order_no에 인덱스가 없음
```text
Table/Index Scan
→ 많은 Index Record 조사
→ Lock 범위 확대
→ 다른 Transaction과 충돌
→ Lock Wait
→ Deadlock 가능성 증가
```
따라서 **동시성 문제에서 SQL보다 먼저 실행계획과 인덱스를 확인해야 하는 경우가 많습니다.**
특히:
```sql
SELECT ...
FOR UPDATE
```
- 에 Index가 없으면 위험도가 더욱 높아집니다.

## 8. 실무 패턴 ① 재고 차감
### 8-1. 사용하면 안 되는 형태
```java
int stock = stockDao.selectStock(productId);
if (stock >= quantity) {
    stockDao.updateStock(productId, stock - quantity);
}
```
동시에 두 요청이 발생하면:
```text
Thread A                  Thread B
   │                         │
SELECT stock=10          SELECT stock=10
   │                         │
stock=9                  stock=9
   │                         │
UPDATE 9                 UPDATE 9
```
원래:
```text
10 → 9 → 8
```
이어야 하지만:
```text
10 → 9
```
가 될 수 있습니다.
이것이 대표적인 **Lost Update Application Pattern**입니다.
### 8-2. 가장 권장하는 형태
DB에서 원자적으로 처리합니다.
```sql
UPDATE product_stock
SET available_qty = available_qty - #{quantity}
WHERE product_id = #{productId}
  AND available_qty >= #{quantity};
```
Java:
```java
int affectedRows = stockMapper.decreaseStock(productId, quantity);
if (affectedRows != 1) {
    throw new InsufficientStockException();
}
```
이 방식이 `SELECT FOR UPDATE → UPDATE`보다 단순하고 Lock 보유시간도 짧습니다.
```text
UPDATE 실행
  ↓
X Lock
  ↓
수량검사 + 차감
  ↓
COMMIT
  ↓
Lock 해제
```
- **재고 차감처럼 단일 Row를 조건부 변경하는 경우에는 이 방식이 우선 선택입니다.**

## 9. 실무 패턴 ② SELECT FOR UPDATE
읽은 정보를 기준으로 여러 가지 비즈니스 판단을 해야 한다면 사용합니다.
예:
```sql
SELECT product_id,
       available_qty,
       sale_status
FROM product_stock
WHERE product_id = #{productId}
FOR UPDATE;
```
Spring:
```java
@Transactional(
    propagation = Propagation.REQUIRED,
    isolation = Isolation.READ_COMMITTED,
    rollbackFor = Exception.class
)
public void order(Long productId, int quantity) {
    ProductStock stock = stockMapper.selectForUpdate(productId);
    if (stock.getAvailableQty() < quantity) {
        throw new InsufficientStockException();
    }
    stockMapper.decrease(productId, quantity);
    orderMapper.insertOrder(...);
}
```
`FOR UPDATE`는 **반드시 실제 Transaction 안에서 실행해야 합니다.** InnoDB에서는 autocommit 상태의 단독 `FOR UPDATE`는 기대하는 장시간 Lock 효과를 얻을 수 없습니다. 
- Spring `@Transactional` 안이면 Spring TransactionManager가 JDBC Connection을 해당 트랜잭션에 바인딩하므로 정상적으로 사용할 수 있습니다.

## 10. FOR UPDATE WAIT / NOWAIT
MariaDB는 다음을 지원합니다.
```sql
SELECT ...
FOR UPDATE WAIT 3;
```
3초만 기다립니다.
```sql
SELECT ...
FOR UPDATE NOWAIT;
```
Lock을 얻지 못하면 바로 실패합니다. MariaDB의 `WAIT n`, `NOWAIT`는 locking read의 Lock wait 시간을 SQL 단위로 조절할 수 있습니다. 
온라인 요청에서:
```text
무조건 50초 기다림
```
보다는:
```text
빠른 실패
→ Application 재시도
→ 사용자 응답
```
- 가 나은 경우가 많습니다.

## 11. MariaDB 10.6의 중요한 기능: SKIP LOCKED
MariaDB 10.6부터 `SKIP LOCKED`가 지원됩니다. Lock을 얻을 수 없는 Row는 기다리지 않고 결과에서 제외합니다. 
예를 들어 Batch Worker가 4개 있다고 가정합니다.
```sql
SELECT job_id
FROM batch_job
WHERE status = 'READY'
ORDER BY job_id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```
```text
Worker-1 → Job 1~100 Lock
Worker-2 → 이미 Lock된 행 Skip → 다음 작업
Worker-3 → 다음 작업
Worker-4 → 다음 작업
```
따라서:
```text
다중 Worker
Queue Consumer
Batch 병렬처리
Outbox 처리
```
에 매우 유용합니다.
반대로 재고 처리에서는:
```text
상품이 Lock되어 있으니 그냥 Skip
```
- 하면 업무상 잘못된 결과가 될 수 있으므로 `SKIP LOCKED`를 무조건 적용해서는 안 됩니다.

## 12. 실무 패턴 ③ 낙관적 Lock
충돌 빈도가 낮다면 `FOR UPDATE`보다 낙관적 Lock이 효율적입니다.
테이블:
```sql
CREATE TABLE orders (
    order_id BIGINT NOT NULL,
    status VARCHAR(20),
    version BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY(order_id)
);
```
조회:
```sql
SELECT order_id,
       status,
       version
FROM orders
WHERE order_id = #{orderId};
```
변경:
```sql
UPDATE orders
SET status = #{status},
    version = version + 1
WHERE order_id = #{orderId}
  AND version = #{version};
```
Thread A/B가 동시에 version=10을 조회:
```text
A UPDATE WHERE version=10
→ 성공
→ version=11
B UPDATE WHERE version=10
→ affectedRows=0
```
Java:
```java
int updated = orderMapper.updateWithVersion(order);
if (updated != 1) {
    throw new ConcurrentUpdateException();
}
```
### 12-1. 권장 대상
```text
상품정보 수정
주문 상태 수정
게시물 수정
사용자 설정
관리자 화면
```
### 12-2. 비권장
초당 수백/수천 요청이 같은 Row에 집중되는:
```text
핫딜 재고
선착순 쿠폰
공용 카운터
```
- 에서는 충돌과 재시도가 너무 많아질 수 있습니다.

## 13. 실무 패턴 ④ UNIQUE Constraint
동시성 문제를 Java `if`로 막으려는 것은 위험합니다.
잘못된 방식:
```sql
SELECT COUNT(*)
FROM payment
WHERE transaction_id = ?;
```
```java
if (count == 0) {
    insert();
}
```
동시에:
```text
A SELECT = 0
B SELECT = 0
A INSERT
B INSERT
```
둘 다 통과할 수 있습니다.
DB 제약조건을 사용해야 합니다.
```sql
ALTER TABLE payment
ADD CONSTRAINT UK_PAYMENT_TX
UNIQUE(transaction_id);
```
그리고:
```sql
INSERT INTO payment(
    transaction_id,
    amount
)
VALUES(
    #{transactionId},
    #{amount}
);
```
Spring에서는 Unique Constraint 위반을 `DuplicateKeyException` 등 `DataAccessException` 계층으로 변환할 수 있습니다. 
커머스에서는 다음에 적극적으로 사용해야 합니다.
```text
payment_transaction_id
order_no
external_request_id
coupon_id + member_id
event_id + member_id
idempotency_key
```
즉:
> **동시성 제어를 Java 코드만으로 하지 말고 DB Constraint까지 마지막 방어선으로 두는 것이 중요합니다.**

## 14. Deadlock
### 14-1. 대표적인 Deadlock
Transaction A:
```text
상품 100 Lock
↓
상품 200 Lock 요청
```
Transaction B:
```text
상품 200 Lock
↓
상품 100 Lock 요청
```
결과:
```text
A
100 Lock
 │
 ▼
200 필요 ──────────────┐
                      │
                      │
B                     │
200 Lock              │
 │                    │
 ▼                    │
100 필요 ─────────────┘
DEADLOCK
```
InnoDB는 Deadlock을 감지하면 한 Transaction을 rollback victim으로 선정합니다. MariaDB Deadlock 오류는:
```text
Error : 1213
SQLSTATE : 40001
ER_LOCK_DEADLOCK
```
입니다. 
### 14-2. 가장 중요한 해결책
Lock 획득 순서를 동일하게 합니다.
잘못된 구조:
```text
A : product 100 → product 200
B : product 200 → product 100
```
수정:
```text
항상 product_id 오름차순
A : 100 → 200
B : 100 → 200
```
예:
```java
productIds.sort(Long::compareTo);
for (Long productId : productIds) {
    stockMapper.selectForUpdate(productId);
}
```
- 이것만으로도 실무 Deadlock 상당수를 줄일 수 있습니다.

## 15. Lock Wait Timeout과 Deadlock은 다르다
|구분|Lock Wait Timeout|Deadlock|
|---|---|---|
|Error|1205|1213|
|SQLSTATE|HY000|40001|
|의미|Lock을 너무 오래 기다림|서로 Lock을 기다리는 순환 발생|
|DB 처리|Timeout까지 대기|감지 즉시 victim rollback|
|Application|Rollback + 필요시 retry|Rollback + retry 권장|
MariaDB 기본 `innodb_lock_wait_timeout`은 50초입니다. 이 timeout은 Deadlock에는 적용되지 않습니다. Deadlock은 별도로 즉시 감지됩니다. 
확인:
```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
```
온라인 커머스에서는 50초가 너무 길 수 있으므로 시스템 특성에 따라:
```sql
SET SESSION innodb_lock_wait_timeout = 5;
```
같이 낮추는 것을 검토할 수 있습니다.
다만 **3초/5초/10초 중 어느 값이 정답인지는 TPS, Transaction 시간, Batch 동시 실행 여부를 Load Test해서 결정해야 합니다.**
매우 중요한 점 하나가 더 있습니다. MariaDB 기본:
```text
innodb_rollback_on_timeout = 0
```
에서는 Lock Wait Timeout 발생 시 기본적으로 **전체 Transaction이 아니라 실패한 Statement만 rollback**될 수 있습니다. 
따라서 Spring에서 1205를 잡고 계속 진행하면 위험합니다.
잘못된 코드:
```java
@Transactional
public void process() {
    dao.updateA();
    try {
        dao.updateB();
    } catch (Exception e) {
        // 무시
    }
    dao.updateC();
}
```
`updateB()`에서 Lock Timeout이 발생했는데 예외를 삼키면 A/C가 Commit되는 잘못된 업무 결과가 만들어질 수 있습니다.
- **Lock 관련 DB Exception은 원칙적으로 Transaction 전체를 rollback하도록 설계하는 것을 권장합니다.**

## 16. Deadlock은 "완전히 없애는 것"이 목표가 아니다
동시성이 높은 DB에서 Deadlock을 100% 제거하려는 설계는 오히려 비효율적일 수 있습니다.
실무 목표는:
```text
Deadlock 발생 빈도를 낮춘다.
        +
발생하면 안전하게 rollback한다.
        +
짧은 횟수만 retry한다.
```
입니다.
예:
```java
for (int retry = 0; retry < MAX_RETRY_COUNT; retry++) {
    try {
        orderService.process(...);
        return;
    } catch (CannotAcquireLockException e) {
        if (retry == MAX_RETRY_COUNT - 1) {
            throw e;
        }
        sleep(...);
    }
}
```
다만 **같은 `@Transactional` 메소드 내부에서 catch해서 동일 Transaction을 retry하면 안 됩니다.**
```text
Retry
  │
  └─ 새 Transaction
       │
       └─ Business 처리
```
- 형태로 외부 Retry 계층과 Transaction 계층을 분리하는 것이 안전합니다.

|Isolation|DEFAULT|
|readOnly|false|

Spring 5.3 공식 문서의 기본 동작입니다. 
`Isolation.DEFAULT`는:

- 가 됩니다.

## 20. Spring 5.3 권장 Transaction 설정
일반 조회:
```java
@Transactional(readOnly = true)
public Product getProduct(Long productId) {
    return productMapper.selectProduct(productId);
}
```
일반 변경:
```java
@Transactional(
    propagation = Propagation.REQUIRED,
    rollbackFor = Exception.class
)
public void updateProduct(Product product) {
    productMapper.updateProduct(product);
}
```
고동시성 주문:
```java
@Transactional(
    propagation = Propagation.REQUIRED,
    isolation = Isolation.READ_COMMITTED,
    timeout = 5,
    rollbackFor = Exception.class
)
public void createOrder(OrderRequest request) {
    // 재고 처리

    // 결제정보 저장 등
```

```java

```
을 넣는 것보다는:
```text

       ↓
대부분 DEFAULT 사용
       ↓
특수 고경합 Transaction만 명시
```
가 관리하기 쉽습니다.

## 21. `@Transactional`은 Service 계층에 두는 것이 좋다

```text
Controller
    ↓
Service @Transactional
    ↓
DAO / Mapper
    ↓
MariaDB
```
예:


```text
Business Rule
```
만 넣습니다.

```text
REST API
PG 요청
메일
SMS
파일 전송
긴 계산
외부 검색 서버
sleep
```

왜냐하면:
```text

  ↓

  ↓
외부 HTTP 호출 5초
  ↓
DB Lock 5초 유지
  ↓

  ↓
```

## 22. Spring `@Transactional` Self Invocation 주의
다음 코드는 문제가 있습니다.
```java
public void process() {

}
@Transactional

}
```

같은 객체 내부에서:

가 호출되면 Spring 기본 Proxy 방식에서는 Transaction Proxy를 거치지 않으므로 `@Transactional`이 적용되지 않습니다. Spring 5.3의 기본 transaction advice mode는 proxy입니다.

```text
OrderFacade
   ↓ proxy
```

## 23. Spring TransactionManager 설정
JDBC/MyBatis 기반이면:
```java
@Bean
public PlatformTransactionManager transactionManager(DataSource dataSource) {
    return new JdbcTransactionManager(dataSource);
}
```
Spring 5.3부터 `JdbcTransactionManager`가 제공되며 `DataSourceTransactionManager`의 확장 형태로 commit/rollback 시 JDBC exception translation까지 제공하므로 신규 JDBC 기반 구성에서는 검토할 가치가 있습니다. 기존 `DataSourceTransactionManager`도 정상적인 선택입니다. 
Java Config:
```java
@Configuration
@EnableTransactionManagement
public class TransactionConfig {
    @Bean
    public PlatformTransactionManager transactionManager(DataSource dataSource) {
        JdbcTransactionManager transactionManager =
                new JdbcTransactionManager(dataSource);
        transactionManager.setValidateExistingTransaction(true);
        return transactionManager;
    }
}
```
`setValidateExistingTransaction(true)`는 상당히 유용합니다.
예:
```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void outer() {
    inner();
}
@Transactional(isolation = Isolation.READ_COMMITTED)
public void inner() {
}
```
- `REQUIRED`로 기존 Transaction에 참가하면 inner의 isolation은 새 Transaction을 만들지 않기 때문에 일반적으로 적용되지 않습니다. Spring 문서에서도 isolation/timeout은 새 Transaction에만 적용된다고 명시하고 있습니다. `validateExistingTransaction=true`를 사용하면 이런 잘못된 조합을 조기에 검출할 수 있습니다.

## 24. XML 기반 Spring 5.3 설정
기존 Spring/eGov 형태라면:
```xml
<bean id="transactionManager"
      class="org.springframework.jdbc.support.JdbcTransactionManager">
    <property name="dataSource" ref="dataSource"/>
    <property name="validateExistingTransaction" value="true"/>
```

도 충분합니다.
- Spring 5.3에서 `@EnableTransactionManagement` 또는 `<tx:annotation-driven/>`이 annotation 기반 Transaction Proxy를 활성화합니다.

## 25. DBCP2와 Isolation 설정
DBCP2는 Connection 기본 Isolation을 지정할 수 있습니다.
```text
defaultTransactionIsolation
```
지원 값은:
```text
READ_UNCOMMITTED
READ_COMMITTED
REPEATABLE_READ
SERIALIZABLE
```
입니다. 
그러나 저는 **DBCP에서 무조건 READ_COMMITTED를 박아두는 방식보다 DB 기본값과 Spring Transaction 정책을 명확하게 관리하는 방식을 권장**합니다.
즉:
```text
MariaDB 기본
      ↓
DataSource
      ↓
@Transactional(isolation=DEFAULT)
```
를 기본으로 하고 필요한 업무만:
```java
@Transactional(isolation = Isolation.READ_COMMITTED)
```
으로 override합니다.
- Spring은 Transaction 시작 시 JDBC Connection에 Transaction 특성을 적용하고 Transaction 종료 후 기존 Isolation을 복원하도록 처리합니다.

## 26. `readOnly=true` 주의
```java
@Transactional(readOnly = true)
```
는 기본적으로:
```text
쓰기 금지 보안 기능
```
으로 생각하면 안 됩니다.
Spring의 `readOnly`는 TransactionManager와 Driver가 활용할 수 있는 최적화 hint의 성격을 가집니다. 
따라서:
```java
@Transactional(readOnly = true)
public void method() {
    mapper.update(...);
}
```
라고 해서 모든 환경에서 반드시 DB가 UPDATE를 막아준다고 가정하면 안 됩니다.
그리고 특히:
```java
@Transactional(readOnly = true)
SELECT ... FOR UPDATE
```
- 는 의미적으로 모순되므로 사용하지 않는 것을 권장합니다.

## 27. `REQUIRES_NEW`와 Connection Pool
다음 구조:
```java
@Transactional
public void order() {
    ...
    auditService.save();
}
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void save() {
}
```
에서는:
```text
Outer Transaction
Connection #1 유지
         │
         └─ REQUIRES_NEW
                ↓
         Connection #2 필요
```
가 됩니다.
100개 Thread가 동시에:
```text
Connection #1 = 100개 사용
그리고 각각 Connection #2 요청
```
하는데:
```text
DBCP maxTotal = 100
```
이면:
```text
모든 Thread가 Connection #1 보유
+
모든 Thread가 Connection #2 대기
```
하는 Connection Pool starvation이 발생할 수 있습니다.
Spring 공식 문서도 `REQUIRES_NEW`가 외부 Transaction의 Connection을 유지한 상태에서 새로운 Connection을 요구하므로 Pool 고갈 및 잠재적인 Deadlock을 일으킬 수 있다고 경고합니다. 
- 따라서 `REQUIRES_NEW`는 정말 필요한 경우만 사용해야 합니다.

## 28. Timeout을 혼동하면 안 된다
실무에서는 다음 네 가지가 완전히 다른 Timeout입니다.
|설정|대상|예|
|---|---|---|
|DBCP `maxWaitMillis`|Connection Pool 획득 대기|5000ms|
|Spring `@Transactional(timeout=)`|Transaction|5초|
|`innodb_lock_wait_timeout`|DB Lock 획득 대기|5초|
|Statement Query Timeout|SQL 실행시간|5초|
DBCP의 `maxWaitMillis`는 Pool에서 Connection 하나를 빌리는 최대 대기시간이지 DB Lock Timeout이 아닙니다. 
예:
```text
Request
 │
 ├─ Pool Connection 기다림 ───── maxWaitMillis
 │
 ▼
Transaction 시작 ─────────────── @Transactional timeout
 │
 ▼
UPDATE
 │
 ├─ DB Lock 기다림 ───────────── innodb_lock_wait_timeout
 │
 └─ Query 실행 ───────────────── query timeout
```
- 이 네 값을 서로 독립적으로 관리해야 합니다.

## 29. 실무 권장 동시성 처리 Pattern

| 업무             | 우선 권장                                 |
| -------------- | ------------------------------------- |
| 재고 단일 차감       | 조건부 Atomic UPDATE                     |
| 중복 주문 방지       | UNIQUE Key                            |
| PG Callback 중복 | Idempotency Key + UNIQUE              |
| 상품 관리자 수정      | Optimistic Lock(version)              |
| 주문 상태 변경       | Optimistic Lock 또는 조건부 UPDATE         |
| 복합 재고 판단       | FOR UPDATE                            |
| 여러 상품 Lock     | 정렬 후 동일 순서 FOR UPDATE                 |
| Batch 작업 분배    | FOR UPDATE SKIP LOCKED                |
| 쿠폰 선착순         | Atomic UPDATE + UNIQUE                |
| 장시간 보고서 조회     | readOnly Transaction, 필요하면 별도 Read DB |
| 고경합 Range 처리   | READ COMMITTED 검토                     |

## 30. 가장 권장하는 주문/재고 구현 형태
예를 들어 다음 정도가 실무적으로 안정적입니다.
```text
Controller
    │
    ▼
OrderService
@Transactional
    │
    ├─ ① 주문 요청 중복 확인
    │       UNIQUE KEY
    │
    ├─ ② 재고 Atomic UPDATE
    │       UPDATE stock
    │       SET qty = qty - ?
    │       WHERE product_id = ?
    │         AND qty >= ?
    │
    ├─ ③ affectedRows 검사
    │       0 → 품절
    │
    ├─ ④ order INSERT
    │
    └─ ⑤ COMMIT
```
SQL:
```sql
UPDATE product_stock
SET available_qty = available_qty - #{orderQty},
    updated_at = CURRENT_TIMESTAMP
WHERE product_id = #{productId}
  AND available_qty >= #{orderQty};
```
Java:
```java
@Transactional(
    propagation = Propagation.REQUIRED,
    rollbackFor = Exception.class,
    timeout = 5
)
public void createOrder(OrderRequest request) {
    int updated = stockMapper.decreaseStock(
            request.getProductId(),
            request.getQuantity());
    if (updated != 1) {
        throw new InsufficientStockException();
    }
    orderMapper.insertOrder(request);
}
```
가능하면:
```text
SELECT stock
→ Java에서 검사
→ UPDATE
```
보다:
```text
조건을 포함한 UPDATE
→ affectedRows 검사
```
- 를 먼저 고려하는 것이 좋습니다.

## 31. 여러 상품 주문 시 Deadlock 방지
장바구니가:
```text
상품 100
상품 200
상품 300
```
이라면 애플리케이션에서 먼저:
```java
items.sort(Comparator.comparing(OrderItem::getProductId));
```
항상:
```text
100 → 200 → 300
```
순으로 업데이트합니다.
```java
@Transactional(rollbackFor = Exception.class)
public void createOrder(List<OrderItem> items) {
    items.sort(Comparator.comparing(OrderItem::getProductId));
    for (OrderItem item : items) {
        int updated = stockMapper.decreaseStock(
                item.getProductId(),
                item.getQuantity());
        if (updated != 1) {
            throw new InsufficientStockException();
        }
    }
    orderMapper.insert(...);
}
```
- 이 **일관된 Lock 순서**는 Deadlock 방지에서 매우 중요합니다.

## 34. 최종적으로 가장 중요한 7가지
1. **`SELECT → Java 계산 → UPDATE`보다 조건부 Atomic UPDATE를 우선 사용합니다.**
2. **중복 방지는 `SELECT COUNT`가 아니라 DB의 PK/UNIQUE Constraint를 마지막 방어선으로 둡니다.**
3. **`FOR UPDATE`는 반드시 Spring Transaction 내부에서 사용하고, 조건 컬럼에 적절한 인덱스를 둡니다.**
4. **여러 Row를 변경할 때 PK 등의 기준으로 Lock 순서를 항상 동일하게 만듭니다.**
5. **Transaction 내부에서 HTTP/PG/메일/파일 등 장시간 외부 I/O를 하지 않습니다.**
6. **`READ COMMITTED`는 유용하지만 Deadlock 해결을 목적으로 무조건 DB 전체에 적용하지 말고 실제 Gap Lock/Range Lock 문제가 확인된 후 적용합니다.**
7. **1205 Lock Timeout과 1213 Deadlock을 정상적인 장애 가능성으로 보고 Rollback + 제한적 Retry 구조를 설계합니다.**
특히 Spring 5.3 + MariaDB 10.6 커머스 구조에서는 **`Atomic UPDATE + UNIQUE KEY + Service @Transactional + 필요한 부분만 FOR UPDATE + Deadlock Retry`가 가장 실용적인 기본 아키텍처**입니다.
