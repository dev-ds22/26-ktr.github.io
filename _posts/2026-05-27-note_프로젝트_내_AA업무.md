### 1. AA 관점에서 주의 할 점
#### 1-1. AA 관점 종합 결론

4월 이후 문의 흐름을 기준으로 보면, 현재 Spring 5.3 기반 커머스 프로젝트에서 가장 주의 깊게 봐야 할 핵심은 **기능 개발 자체보다 트랜잭션 경계, DB Connection Pool, Mail DB 분리, 배치 정합성, 모니터링 체계, 배포 파이프라인의 운영 안정성**입니다. 특히 `Main DB + Mail DB`를 하나의 흐름으로 묶는 구조, `ChainedTransactionManager`, 전체 Service 대상 광범위 트랜잭션 AOP, DBCP2 Pool 고갈, Mail DB Pool 병목은 장애 시 영향 범위가 커질 가능성이 높습니다. Spring의 트랜잭션 관리는 Service/Data Access 계층 간 경계 설계가 핵심이며, 선언적 트랜잭션은 AOP 기반으로 동작하므로 적용 범위와 호출 구조를 명확히 해야 합니다. ([Home](https://docs.spring.io/spring-framework/docs/5.3.x/reference/html/data-access.html?utm_source=chatgpt.com "Data Access"))

#### 1-2. 최우선으로 봐야 할 위험 영역

|우선|영역|현재 우려|AA 판단|
|--:|---|---|---|
|1|트랜잭션|`ChainedTransactionManager`로 Main/Mail DB 묶음|부분 커밋·정합성 불일치 위험 최상|
|2|AOP 범위|전체 `*Service.*(..)`에 일괄 트랜잭션|조회/외부 API/메일까지 트랜잭션이 과도하게 확장될 수 있음|
|3|Mail DB|Main DB와 Mail DB Pool 크기 차이|Mail DB 병목이 Main 업무 Thread까지 지연시킬 수 있음|
|4|DBCP2|Pool 고갈·idle 검증·DB/L4 timeout|장애 원인 추적이 어려우므로 지표화 필요|
|5|배치|DuplicateKey, autocommit, chunk rollback 혼선|데이터 중복·부분 반영·재처리 설계 필요|
|6|모니터링|OS TCP 상태와 Pool 상태 혼용|`ESTAB`만으로 Active/Idle 판단하면 오판 가능|
|7|배포|GitLab/Jenkins/SonarQube/QA 브랜치|품질 게이트와 배포 실패 기준 분리 필요|

#### 1-3. 트랜잭션 구조에서 가장 위험한 부분

현재 구조상 핵심 위험은 `txManager(dataSource)`와 `txManagerMail(dataSourceMail)`을 `ChainedTransactionManager`로 묶고, 이를 Service 전체 AOP에 적용하는 방식입니다. `ChainedTransactionManager`는 Spring Framework 본체가 아니라 Spring Data Commons의 클래스이며 공식 Javadoc에서 Deprecated로 표시되어 있고, 일부 트랜잭션이 이미 커밋된 뒤 다른 트랜잭션 커밋이 실패하면 부분 커밋 상태가 발생할 수 있다고 설명합니다. ([Home](https://docs.spring.io/spring-data/commons/docs/current/api/org/springframework/data/transaction/ChainedTransactionManager.html?utm_source=chatgpt.com "ChainedTransactionManager (Spring Data Core 4.0.5 API)"))

|항목|주의 내용|
|---|---|
|Main DB 커밋 성공 후 Mail DB 커밋 실패|주문/업무 데이터는 반영됐지만 메일 이력은 실패 가능|
|Mail DB 장애|핵심 업무 트랜잭션까지 실패 또는 지연시킬 가능성|
|`rollback-for="Exception"` 전체 적용|단순 부가 기능 오류가 전체 업무 롤백으로 확대 가능|
|전체 Service `REQUIRED`|조회, 메일, 외부 API 호출까지 불필요하게 트랜잭션에 포함될 수 있음|
|Self-invocation|같은 클래스 내부 메서드 호출은 AOP 트랜잭션이 적용되지 않을 수 있음|

#### 1-4. 앞으로의 트랜잭션 설계 방향

|구분|권장 방향|
|---|---|
|핵심 업무|Main DB 전용 `txManager` 사용|
|메일 이력|`txManagerMail` 별도 적용|
|메일 발송|Main DB commit 이후 처리|
|정합성 보완|Outbox Table, 재처리 상태값, 실패 이력 관리|
|AOP 적용|전체 `*Service.*`보다 업무 성격별 pointcut 분리|
|조회성 메서드|read-only 트랜잭션 또는 트랜잭션 미적용 검토|
|가장 안전한 방향은 **Main DB 업무 트랜잭션과 Mail DB/메일 발송 트랜잭션을 분리**하는 것입니다. 커머스 업무에서 주문, 결제, 회원, 상품 같은 핵심 데이터는 Main DB 기준으로 먼저 안정화하고, 메일·알림·이력성 데이터는 실패해도 재처리 가능한 구조로 분리해야 합니다.||

#### 1-5. DBCP2 Connection Pool에서 주의할 점

DBCP2의 `maxTotal`은 동시에 할당 가능한 최대 Connection 수이고, `initialSize`는 Pool 시작 시 생성되는 초기 Connection 수입니다. `getNumActive()`는 현재 빌려간 객체 수, `getNumIdle()`은 Pool에 남아 있는 idle 객체 수를 의미하므로, 운영 판단은 `maxTotal`, `numActive`, `numIdle`, `maxWait`를 함께 봐야 합니다. ([Apache Commons](https://commons.apache.org/dbcp/configuration.html?utm_source=chatgpt.com "BasicDataSource Configuration – Apache Commons DBCP"))

|위험|설명|대응|
|---|---|---|
|Main 100 / Mail 10|Mail DB Pool이 먼저 고갈될 수 있음|Mail 처리 분리, 비동기화, 별도 지표화|
|`maxTotal=1` 테스트 설정|동시 요청 2개만 와도 대기 발생|운영 설정과 테스트 설정 구분|
|`Timeout waiting for idle object`|Pool에서 빌릴 Connection이 없음|장기 SQL, 트랜잭션 범위, 누수, Lock 확인|
|stale connection|DB/L4 idle timeout 후 죽은 연결 재사용|`testOnBorrow`, `testWhileIdle`, evictor 검토|
|idle 과다|DB connection 낭비|`minIdle`, `maxIdle`, DB `max_connections`와 함께 산정|

#### 1-6. DB Connection 모니터링 기준

OS 명령어의 `ss` 결과는 **WAS와 DB 사이의 TCP 연결 상태**입니다. 반면 DBCP2의 `active/idle`은 **Pool 내부의 대여 상태**입니다. 따라서 `ESTAB = DBCP2 Active`로 보면 안 되고, 보통 `ESTAB`는 `active + idle`에 가까운 TCP 연결 수로 해석해야 합니다.

|지표|계층|의미|
|---|---|---|
|`ESTAB`|OS TCP|WAS와 DB 간 연결 성립|
|`TIME-WAIT`|OS TCP|연결 종료 후 대기|
|`CLOSE-WAIT`|OS TCP|상대가 닫았으나 로컬이 아직 정리하지 않음|
|`numActive`|DBCP2|애플리케이션이 빌려 사용 중|
|`numIdle`|DBCP2|Pool에 반납되어 대기 중|
|`maxTotal`|DBCP2|Pool 최대 허용 수|
|운영 모니터링은 아래처럼 2계층으로 나누는 것이 맞습니다.|||

```text
1. OS 관점: ss/netstat로 TCP 상태 확인
2. Application 관점: Micrometer/JMX로 DBCP2 active, idle, maxTotal 확인
```

Micrometer는 여러 모니터링 시스템에 대한 facade 역할을 하며, Prometheus Registry는 Prometheus가 scrape할 수 있는 형식으로 metric을 노출하는 방식입니다. Spring Boot Actuator가 없는 Spring 5.3 환경에서는 `PrometheusMeterRegistry`와 endpoint를 직접 구성해야 합니다. ([Micrometer Application Observability](https://micrometer.io/?utm_source=chatgpt.com "Micrometer Application Observability"))

#### 1-7. 현재 커맨드 기반 모니터링 시 주의점

최근 정리한 `watch + ss + awk` 커맨드는 운영 중 빠른 확인용으로 유용합니다. 다만 이 커맨드는 TCP 상태만 보기 때문에, 장애 판단 시 아래처럼 사용해야 합니다.

|관찰|가능한 해석|추가 확인|
|---|---|---|
|`ESTAB` 증가|Pool 생성 증가 또는 idle 유지|DBCP2 `numActive/numIdle`|
|`ESTAB`는 높고 `numActive` 낮음|idle connection이 많음|`minIdle/maxIdle` 적정성|
|`ESTAB` 높고 `numActive`도 높음|실제 DB 사용량 증가|SQL, Thread, Lock|
|`CLOSE-WAIT` 증가|소켓 정리 지연 가능|JDBC close, Driver, WAS 로그|
|`TIME-WAIT` 급증|짧은 연결 반복 생성/종료|Pool 미사용 또는 연결 재생성 의심|

#### 1-8. Spring Batch와 데이터 정합성

4월 이후 배치 관련 문의에서는 `DuplicateKeyException`, `BatchUpdateException`, `commit-interval`, `autocommit=1`, skip/retry 처리 문제가 반복되었습니다. AA 관점에서는 배치가 단순히 “오류 row skip”으로 끝나는 문제가 아니라, **재실행 가능성, 중복 방지, chunk 단위 원자성, 부분 반영 후 복구 방식**을 명확히 해야 합니다.

|항목|주의 내용|
|---|---|
|DuplicateKey|기존 데이터 존재 시 재처리 정책 필요|
|autocommit=1|Spring Batch 트랜잭션 기대와 실제 DB 반영이 어긋날 수 있음|
|commit-interval|1000건 단위 rollback 기대가 실제와 다를 수 있음|
|skip/retry|어떤 예외를 skip하고 어떤 예외를 중단할지 기준 필요|
|재실행|동일 Job 재실행 시 중복 insert 방지 필요|
|Writer|MyBatis Batch Writer 사용 시 flush 시점과 예외 발생 위치 확인 필요|
|배치성 데이터는 `INSERT only`보다 `UPSERT`, `MERGE 유사 처리`, 선삭제/후삽입, 처리 상태 테이블, 중복 키 사전 필터링 중 하나를 명확히 선택해야 합니다.||

#### 1-9. 배포/품질 파이프라인에서 주의할 점

현재 문의 흐름상 GitLab → Jenkins → Maven Build → SonarQube → Quality Gate → Deploy 구조를 다루고 있습니다. AA 관점에서는 “QA 브랜치를 추가할 수 있는가”보다, **브랜치별 배포 환경과 품질 게이트 실패 시 배포 차단 기준을 어떻게 둘 것인가**가 더 중요합니다.

|영역|주의 내용|
|---|---|
|Branch|`feature → dev → qa → prd` 흐름 명확화|
|Jenkins Profile|Maven profile과 Git branch 매핑 검증|
|SonarQube|projectKey를 브랜치/환경별로 분리할지 결정|
|Quality Gate|dev에서 경고, qa/prd에서 차단 등 단계별 기준 필요|
|Nexus|dev/qa/prd artifact 저장소 분리 또는 naming 정책 필요|
|Rollback|배포 실패 시 이전 artifact 복구 절차 필요|
|권한|SonarQube Project Settings 접근권한, Jenkins credential 관리 필요|

#### 1-10. 앞으로 특히 조심해야 할 설계 패턴

|패턴|위험|
|---|---|
|모든 Service에 동일 트랜잭션 적용|업무 성격별 최적화 불가, 장애 영향 범위 확대|
|메일/외부 API를 DB 트랜잭션 안에서 호출|외부 지연이 DB Connection 점유 시간 증가|
|DB Pool 크기만 늘려 해결|SQL/Lock/트랜잭션 누수를 가리는 임시 조치가 될 수 있음|
|OS TCP 수만 보고 Pool 판단|Active/Idle 구분 불가|
|`SUPPORTS read-only`를 만능 조회 설정으로 사용|기존 트랜잭션 안에서는 그대로 참여할 수 있음|
|method name 기반 tx rule 과신|메서드명 규칙 누락 시 의도와 다른 트랜잭션 적용 가능|
|ChainedTransactionManager로 정합성 보장 기대|XA/2PC가 아니므로 원자성 보장 불가|

#### 1-11. AA 관점 권장 To-Be 구조

```text
[Controller]
   ↓
[Application Service]
   ├─ Main Business Transaction(txManagerMain)
   │    └─ Main DB
   ├─ afterCommit Event / Outbox 적재
   │    └─ Mail Request / Notification Request
   └─ Async Worker or Scheduler
        └─ Mail DB / Mail API / Retry
```

|구성|권장|
|---|---|
|Main 업무|단일 Main DB 트랜잭션|
|Mail 이력|별도 트랜잭션 또는 Outbox 기반|
|외부 API|DB 트랜잭션 밖에서 호출 권장|
|장애 복구|실패 상태 저장 후 재처리|
|모니터링|DBCP2 + OS TCP + WAS Thread + DB Processlist 통합|
|배포|dev/qa/prd 단계별 품질 기준 분리|

#### 1-12. 앞으로 우선 처리할 작업 목록

|순서|작업|목적|
|--:|---|---|
|1|현재 AOP Transaction pointcut 전체 목록 정리|어떤 Service가 어떤 TX를 타는지 확정|
|2|`transactionManager`가 Chained인지 Main 전용인지 분리|부분 커밋 위험 축소|
|3|Mail DB 사용 Service 분리|Mail 장애가 Main 업무에 미치는 영향 축소|
|4|DBCP2 `main/mail` Pool 지표 수집|장애 시 수치 기반 판단|
|5|`ss` 모니터링과 Micrometer 지표 비교|OS/TCP와 Pool 상태 오판 방지|
|6|Batch 중복 처리 정책 문서화|재실행 안정성 확보|
|7|Jenkins dev/qa/prd pipeline 기준 정리|배포 안정성 확보|
|8|운영 장애 시나리오 작성|Pool 고갈, Mail DB 장애, DB Lock, 배포 실패 대응|

#### 1-13. 최종 권고

현재 프로젝트에서 AA가 가장 먼저 봐야 할 것은 **트랜잭션을 더 강하게 묶는 것**이 아니라 **업무 중요도에 따라 트랜잭션을 분리하고, 실패를 재처리 가능한 구조로 바꾸는 것**입니다. `ChainedTransactionManager`는 부분 커밋 위험 때문에 장기적으로 제거 또는 사용 축소 방향이 맞고, Main DB와 Mail DB는 같은 서버의 다른 스키마라고 해도 운영 장애 관점에서는 별도 리소스로 봐야 합니다. DBCP2는 `maxTotal` 숫자만 조정하지 말고 `active`, `idle`, `wait`, `TCP 상태`, `DB processlist`, `WAS Thread`를 함께 보는 모니터링 체계를 먼저 구축해야 합니다. 배치와 배포는 각각 **재실행 가능성**과 **환경별 품질 게이트 기준**을 명확히 하는 것이 앞으로의 핵심 관리 포인트입니다.
